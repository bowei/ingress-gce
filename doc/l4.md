# L4 Load Balancer Controller Architecture

This document provides a detailed overview of the L4 Load Balancer Controller's architecture within the `ingress-gce` repository.

## Overview

The L4 Controller is responsible for reconciling Kubernetes `Service` resources of `type: LoadBalancer`. It manages both L4 Internal Load Balancers (ILB) and L4 External Network Load Balancers (NetLB) using regional, backend-service based load balancing resources in Google Cloud.

## Controller Initialization

The entry point for the controller is in `cmd/glbc/main.go`. Based on the flags provided, it initializes and starts the necessary controller loops:

-   `--run-l4-controller`: Starts the `L4Controller` for L4 ILB services.
-   `--run-l4-netlb-controller`: Starts the `L4NetLBController` for L4 NetLB services.

Both controllers are initialized with a shared `ControllerContext`, which provides access to Kubernetes and GCP clients, informers for watching resource changes (Services, Nodes, etc.), and resource naming utilities. Each controller runs a specified number of workers (configured via `--num-l4-workers` and `--num-l4-netlb-workers`) to process service changes in parallel.

## Event Handling and Work Queue

The controllers watch for changes to Kubernetes `Service` objects. An event handler determines if a service is relevant and, if so, enqueues its key (in the format `namespace/name`) into a work queue for reconciliation.

A service is enqueued if:
1.  It is a `Service` of `type: LoadBalancer` and has the necessary annotations for either ILB (`cloud.google.com/load-balancer-type: "Internal"`) or NetLB (`cloud.google.com/l4-rbs-enabled: "true"`).
2.  It was previously an L4 load balancer but has been modified to no longer be one (e.g., the annotation was removed or the type was changed). This is necessary for garbage collection.
3.  The service's spec has changed in a way that affects the load balancer configuration (e.g., `ports`, `loadBalancerSourceRanges`, `sessionAffinity`, `externalTrafficPolicy`).
4.  The service has a deletion timestamp, indicating it is being deleted.

The controllers also periodically re-enqueue all relevant services to ensure the state of GCP resources remains consistent with the Kubernetes objects.

## The Sync Loop

A worker pulls a service key from the queue and executes the `sync` function, which is the core of the reconciliation logic. The process is as follows:

1.  **Fetch Service**: The `Service` object is retrieved from the informer's cache.
2.  **Deletion or Update?**: The controller checks if the service `needsDeletion`. This is true if the object has a deletion timestamp OR if it no longer meets the criteria for an L4 load balancer (triggering a cleanup). Otherwise, it proceeds with a create/update flow.

### L4 ILB Controller (`pkg/l4lb/l4controller.go`)

The ILB controller manages services with the `cloud.google.com/load-balancer-type: "Internal"` annotation.

#### Pre-checks
Before processing, the `shouldProcessService` function checks if the service is managed by the legacy (in-tree) service controller. It does this by looking for the legacy finalizer (`service.kubernetes.io/load-balancer-finalizer`) or an existing legacy forwarding rule. This prevents two controllers from fighting over the same service.

#### Create/Update Flow (`processServiceCreateOrUpdate`)
1.  **Finalizer**: Ensures the `gce.networking.io/l4-ilb-v2` finalizer is present on the `Service` object. This prevents the service from being deleted from Kubernetes until the controller has finished cleaning up the associated GCP resources.
2.  **Resource Creation**: The core logic is delegated to `pkg/loadbalancers/l4.go`. The `EnsureInternalLoadBalancer` function is called to create or update all necessary GCP resources (see "GCE Resource Management" below).
3.  **Backend Linking**: The controller's `negLinker` links the zonal Network Endpoint Groups (NEGs) for the service's backends to the regional backend service. The NEGs themselves are managed by the separate NEG controller.
4.  **Status Update**: The `Service`'s `.status.loadBalancer.ingress` field is updated with the IP address of the forwarding rule.
5.  **Annotation Update**: The names of the created GCP resources (e.g., forwarding rule, backend service) are stored as annotations on the `Service` object for future reference.

#### Deletion Flow (`processServiceDeletion`)
1.  **Resource Deletion**: Delegates to `EnsureInternalLoadBalancerDeleted` in `pkg/loadbalancers/l4.go` to delete all associated GCP resources.
2.  **Cleanup**: The controller clears the `.status.loadBalancer.ingress` field, removes the resource annotations, and finally, removes the `gce.networking.io/l4-ilb-v2` finalizer, allowing the Kubernetes API server to delete the `Service` object.

### L4 NetLB Controller (`pkg/l4lb/l4netlbcontroller.go`)

The NetLB controller manages services with the `cloud.google.com/l4-rbs-enabled: "true"` annotation (RBS stands for Regional Backend Service).

#### Pre-checks
The controller first verifies that it should manage the service. The `isRBSBasedService` function checks for the RBS annotation, the v2 finalizer, or an existing RBS-based forwarding rule. Crucially, it also includes logic in `preventLegacyServiceHandling` to avoid conflicts with the legacy target-pool-based external load balancer implementation. If a user accidentally adds the RBS annotation to a service currently managed by the legacy controller, this controller will remove the annotation to prevent a disruptive migration.

#### Create/Update Flow (`syncInternal`)
1.  **Finalizer**: Ensures the `gce.networking.io/l4-netlb-v2` finalizer is present.
2.  **Instance Groups**: For services on the default network, the controller ensures that an unmanaged GCE instance group exists for each zone, containing all eligible nodes in that zone. This is handled by the `instancePool`. For multi-network services, NEGs are used instead.
3.  **Resource Creation**: Delegates to `pkg/loadbalancers/l4netlb.go`. The `EnsureFrontend` function is called to create or update GCP resources.
4.  **Backend Linking**: The controller links the appropriate backends to the backend service. This is done by the `igLinker` for instance groups or the `negLinker` for NEGs (in multi-network scenarios).
5.  **Status & Annotation Update**: Same as the ILB controller.

#### Deletion Flow (`garbageCollectRBSNetLB`)
1.  **Resource Deletion**: Delegates to `EnsureLoadBalancerDeleted` in `pkg/loadbalancers/l4netlb.go`.
2.  **Instance Group Deletion**: Attempts to delete the cluster-wide instance groups if they are no longer needed.
3.  **Cleanup**: Same as the ILB controller (clear status, remove annotations, remove finalizer).

## GCE Resource Management (`pkg/loadbalancers/`)

The `l4.go` and `l4netlb.go` files contain the logic for creating, updating, and deleting the specific GCP resources that constitute a load balancer.

-   **Health Checks**:
    -   A regional health check is created to monitor the health of backend endpoints.
    -   The type of health check depends on the service's `externalTrafficPolicy`.
        -   `Cluster`: A shared health check is used across all services with this policy, as any node can handle the traffic.
        -   `Local`: A dedicated health check is created for the service, as only nodes with local endpoints are valid backends.
    -   A firewall rule is also created to allow health check probes from Google's designated IP ranges (`35.191.0.0/16`, `130.211.0.0/22`) to the nodes.

-   **Backend Service**:
    -   A regional backend service is created.
    -   Its configuration is derived from the `Service` spec, including the protocol (`TCP` or `UDP`), session affinity, and the link to the health check.
    -   For NetLB, it can also be configured with a connection tracking policy to enable Strong Session Affinity.

-   **Forwarding Rules**:
    -   A regional forwarding rule is created to direct incoming traffic to the backend service.
    -   It reserves and assigns the external or internal IP address for the load balancer. The controller contains logic to hold and release IP addresses during updates to prevent IP address churn.
    -   For dual-stack services, separate forwarding rules are created for IPv4 and IPv6 traffic, pointing to the same backend service.

-   **Firewall Rules**:
    -   In addition to the health check firewall, a second firewall rule is created. This rule allows traffic from the user-specified `loadBalancerSourceRanges` to the nodes on the service ports. This ensures that only legitimate traffic can reach the backends.

## Finalizers and Garbage Collection

The use of finalizers is critical to the controller's operation. The finalizer (`gce.networking.io/l4-ilb-v2` or `gce.networking.io/l4-netlb-v2`) is a key that tells the Kubernetes API server not to fully delete a `Service` object as long as the key is present.

This mechanism ensures that if a user deletes a `Service`, the controller has time to perform the asynchronous cleanup of all associated GCP resources. Once the resources are confirmed to be deleted, the controller removes the finalizer, and only then is the `Service` object removed from the Kubernetes API. This prevents orphaned GCP resources and associated costs.
