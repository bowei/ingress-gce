# L7 Ingress Controller Architecture

This document provides a detailed overview of the L7 Ingress Controller's architecture within the `ingress-gce` repository.

## Overview

The L7 Ingress Controller is responsible for reconciling Kubernetes `Ingress` resources by creating and managing Google Cloud L7 external and internal load balancers. It watches for changes to `Ingress`, `Service`, `BackendConfig`, and other related resources and translates them into the appropriate GCE networking resources.

## File Organization

The core components of the L7 controller are organized as follows:

-   **`cmd/glbc/main.go`**: The main entry point for the controller binary. It initializes the Kubernetes client, cloud provider client, and starts all the active controllers, including the `LoadBalancerController`. It's responsible for setting up leader election, which ensures that only one instance of the controller is active at a time.

-   **`pkg/controller/controller.go`**: This file contains the `LoadBalancerController` struct, which is the heart of the L7 controller. It includes the main reconciliation loop (`sync`) and event handlers for Kubernetes resources. The controller watches for changes to Ingresses, Services, and BackendConfigs and enqueues Ingress keys for processing.

-   **`pkg/controller/translator/translator.go`**: The legacy `Translator` is responsible for converting a Kubernetes `Ingress` object into a provider-agnostic `GCEURLMap` object. This `GCEURLMap` represents the desired state of the load balancer's URL map, backend services, and health checks. This is the first major step in the reconciliation process.

-   **`pkg/loadbalancers/l7s.go`**: This file contains the `L7s` struct, which acts as a pool of L7 load balancers (`l7Pool` in the old doc). Its `Ensure` method creates or retrieves an `L7` object, which represents a single load balancer. The `L7` object then manages the lifecycle of high-level GCE load balancer resources, such as forwarding rules, target proxies, and URL maps.

-   **`pkg/backends/syncer.go`**: This file contains the `backendSyncer`. It's responsible for synchronizing the state of GCE backend services based on the `GCEURLMap` generated by the translator. It iterates over the services required by the Ingress and ensures that a corresponding GCE backend service exists with the correct configuration.

-   **`pkg/backends/backends.go`**: This package contains the `Backends` struct, which is a pool for managing backend services. It handles the CRUD (Create, Read, Update, Delete) operations for GCE backend services.

-   **`pkg/healthchecks/healthchecks.go`**: This package manages the GCE health checks associated with backend services. The `backendSyncer` calls this package to ensure that the correct health checks are configured for each backend service. The health check configuration can be derived from a `readinessProbe` on the Pod or from a `BackendConfig` CRD.

-   **`pkg/backends/neg_linker.go`** and **`pkg/backends/ig_linker.go`**: These files contain the logic for linking backends (NEGs or IGs) to backend services. After the backend services are created, the appropriate linker is used to attach the correct set of endpoints.

## Detailed Control Flow

The L7 controller operates in a continuous reconciliation loop. Here's a more detailed breakdown of the workflow:

1.  **Initialization**:
    *   The `main` function in `cmd/glbc/main.go` starts.
    *   It establishes a connection to the Kubernetes API server and the Google Cloud API.
    *   It creates a `ControllerContext` which holds shared components like informers, clients, and the cloud provider.
    *   It instantiates the `LoadBalancerController` from `pkg/controller/controller.go`.
    *   If leader election is enabled, it starts the leader election process. The leader proceeds to run the controller.

2.  **Event Trigger and Enqueue**:
    *   The `LoadBalancerController` has event handlers for `Ingress`, `Service`, and `BackendConfig` resources.
    *   When a change is detected (add, update, delete), the event handler determines which `Ingress` resources are affected.
    *   The key of each affected `Ingress` (in the format `namespace/name`) is added to a work queue (`ingQueue`).

3.  **Sync (Reconciliation)**:
    *   A worker goroutine from the queue picks up an `Ingress` key. This triggers the `sync` method in `LoadBalancerController`.
    *   The `sync` method first performs a pre-sync garbage collection check (`preSyncGC`). If the Ingress is marked for deletion, it triggers the GC process for the associated cloud resources and stops further processing for this Ingress.
    *   If the Ingress is not being deleted, the controller ensures it has a finalizer to handle cleanup correctly upon deletion.
    *   **Translation**: The `Translator` is called to convert the `Ingress` spec into a `GCEURLMap`. This involves parsing the rules, paths, and TLS settings from the Ingress object. This `GCEURLMap` contains a list of `ServicePort` objects, which represent the desired state of the backend services.
    *   The `ingSyncer.Sync` method is called, which orchestrates the synchronization of GCP resources. This process is broken down into two main phases:
        1.  **Backend Sync (`SyncBackends`)**:
            *   The `backendSyncer.Sync` method is called with the list of `ServicePort`s from the `GCEURLMap`.
            *   For each `ServicePort`, the `backendSyncer` calls `ensureBackendService`.
            *   `ensureBackendService` checks if a GCE backend service already exists.
            *   **Health Check Sync**: It calls `healthChecker.SyncServicePort` to create or update the GCE health check for the backend service. The health check can be customized via a Pod's `readinessProbe` or a `BackendConfig`.
            *   **Backend Service Creation/Update**: If the backend service doesn't exist, it's created. If it exists, it's updated with the correct protocol, health check link, and other settings from the `ServicePort` and any associated `BackendConfig` (e.g., CDN, IAP, timeout, session affinity).
            *   **Backend Linking**: After the backend service is synced, the `negLinker` or `igLinker` is called to attach the correct backends (NEGs or IGs) to the backend service.
        2.  **Load Balancer Sync (`SyncLoadBalancer`)**:
            *   The `l7Pool.Ensure` method is called. This creates an `L7` object representing the load balancer.
            *   The `L7` object's `edgeHop` method is called, which orchestrates the creation and configuration of the frontend of the load balancer:
                *   **URL Map**: The `GCEURLMap` is translated into a composite `UrlMap` and synced with GCP.
                *   **Target Proxies**: `TargetHttpProxy` and/or `TargetHttpsProxy` are created or updated. For HTTPS, SSL certificates are attached.
                *   **Forwarding Rules**: `ForwardingRules` are created or updated to route traffic from the load balancer's IP address to the target proxies.

4.  **Status Update (`PostProcess`)**:
    *   After successfully reconciling the GCE resources, the `updateIngressStatus` method is called.
    *   It retrieves the IP address from the forwarding rule and updates the `status.loadBalancer.ingress` field of the `Ingress` resource in Kubernetes.
    *   It also updates annotations on the Ingress object with information about the created GCE resources (e.g., URL map name, forwarding rule name).

5.  **Garbage Collection**:
    *   When an `Ingress` is deleted, its `deletionTimestamp` is set. The `preSyncGC` logic detects this.
    *   The `ingSyncer.GC` method is called, which identifies all GCE resources associated with the deleted Ingress (using the naming scheme).
    *   It then proceeds to delete these resources in the correct order (forwarding rules, target proxies, URL maps, backend services, health checks).
    *   After all associated GCE resources are deleted, the finalizer is removed from the `Ingress` object, allowing the Kubernetes garbage collector to delete it.
    *   The controller also has a periodic GC process (`GCv1`) that lists all GCE resources managed by the controller and deletes any that are not associated with an existing Ingress. This is a safety mechanism to clean up orphaned resources.

This detailed control flow ensures that the state of the GCE load balancer and its components continuously reflects the desired state defined in the Kubernetes `Ingress` and related resources.
